# 관리자 직접 입력 당첨번호

당첨번호는 사이트 운영자가 Supabase 관리 화면에서 입력합니다. 사이트는
이 프로젝트에 등록된 자료를 읽으며 동행복권의 조회 주소를 자동 호출하지 않습니다.
모든 방문자가 같은 등록 결과를 봅니다. 방문자는 당첨번호를 등록·수정할 수 없습니다.

## 최초 설정 한 번

1. 기존 `Luckzip-reviews` 프로젝트의 **SQL Editor → New query**를 엽니다.
2. [20261029_admin_draw_results.sql](migrations/20261029_admin_draw_results.sql)의
   전체 내용을 붙여 넣고 **Run**을 누릅니다.
3. 성공하면 첫 화면을 새로고침해 등록 자료가 표시되는지 확인합니다.

브라우저용 공개 키에는 테이블·함수를 설치할 권한이 없으므로 SQL은 프로젝트
관리자가 직접 실행해야 합니다. 관리자 키나 데이터베이스 비밀번호를 사이트에
추가할 필요는 없습니다.

기존 사이트에 보관했던 **1247회 / 2026-10-24 / 8, 14, 21, 22, 42, 45 /
보너스 24**를 최초 자료로 넣습니다. 이 회차가 이미 있으면 덮어쓰지 않습니다.
다른 회차나 미래의 당첨번호를 임의로 생성하거나 외부 사이트에서 수집하지 않습니다.
SQL을 다시 실행해도 기존 등록 자료와 후기 게시판은 유지됩니다.

## 매주 추첨 결과를 입력하는 방법

1. Supabase **Table Editor**에서 스키마를 **`draws_private`**로 선택합니다.
2. **`draws`** 테이블을 열고 **Insert → Insert row**를 선택합니다.
3. 공식 발표를 확인해 아래 값을 입력합니다.

| 입력 칸 | 입력할 값 |
| --- | --- |
| `draw_no` | 회차 번호, 숫자만 입력 |
| `draw_date` | 실제 추첨일, `YYYY-MM-DD` 형식 |
| `n1` ~ `n6` | 당첨번호 6개를 작은 숫자부터 차례대로 입력 |
| `bonus_number` | 보너스 번호 1개 |
| `created_at`, `updated_at` | 기본값 그대로 두기, 자동 기록 |

4. 저장한 뒤 사이트를 새로고침합니다. 가장 큰 회차의 등록 결과가 첫 화면에
   표시되고, 등록된 과거 회차도 저장 번호 비교에서 조회할 수 있습니다.

당첨번호는 서로 다른 1~45의 숫자 6개여야 하며 보너스는 그 6개와 달라야 합니다.
중복·범위 초과·정렬 오류는 데이터베이스가 저장을 거부합니다. 같은 회차를 고칠
때는 새 행을 만들지 말고 해당 행을 수정합니다. 수정 시각은 자동 갱신됩니다.

한국 시간 기준 미래 날짜로 입력한 자료는 공개 조회에 나타나지 않습니다.
날짜만 검증하므로 추첨 당일의 발표 시각이나 번호의 사실 여부까지 자동 확인하지는
않습니다. 실제 결과가 발표된 뒤 입력하고 저장 전에 한 번 더 대조해야 합니다.
자동으로 다음 회차를 만들거나 당첨번호를 업데이트하지 않습니다.

## 접근 권한

- 관리자는 본인의 Supabase 계정으로 로그인해 입력·수정합니다.
- `draws_private`는 Data API의 공개 스키마에 추가하지 않습니다.
- 공개 사이트는 읽기 전용 `draw_result_get` 함수만 호출합니다.
- 공개 `anon`·`authenticated` 역할과 브라우저 키에는 테이블 읽기·쓰기,
  관리 함수 실행 권한을 부여하지 않습니다.
- 기존 후기 게시판의 비밀번호·접근 권한은 변경하지 않습니다.

## 로컬 검증

Docker와 Python 3가 있는 환경에서 저장소 루트에서 실행합니다.

```sh
python3 supabase/tests/draws.py
```

테스트는 `--network none`인 격리된 PostgreSQL 17 컨테이너를 만들고 제거합니다.
실제 Supabase 프로젝트나 방문자 데이터에 접속하지 않습니다. 결과 등록·조회,
형식 검증, 비공개 데이터 접근 차단, 수정 시각, 미래 날짜 비공개, 반복 실행 시
기존 수정 내용 보존과 후기 데이터 유지 여부를 검사합니다.
